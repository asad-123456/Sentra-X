# Sentra-X UI/UX improvement plan

**Audit date** November 21, 2026  
**Baseline** Local `m08-runtime-settings` working tree over `dc5f5a1`, including the verified but uncommitted M08 runtime-settings work. The audit uses the existing isolated `sentrax-m08` Docker Compose lab and the existing offline frontend build.  
**Scope** Design audit and implementation proposal. The application, its APIs, and its business rules were left as found.

## Executive summary

Sentra-X has the core of a professional SOC console. The role-specific navigation is compact, the queue leads to inspectable evidence, and the operator can see the running model separately from a saved assessment. The strongest next step is to make that review path usable by keyboard and at narrow widths, then make status and benchmark claims match the underlying data.

**Fix first:** focus handling in alert detail, the mobile shell, the queue's unverified “Stream Active” status, and the contradictory offline benchmark count. Keep the dark Sentra-X identity, evidence citations, role boundaries, audit history, and M08's read-only runtime settings.

## Audit method and evidence

Impeccable's **Operate** guidance informed the review. The criteria were fast scanning, visible system state, one clear decision at a time, progressive disclosure, predictable controls, and useful recovery messages. The technical audit covered accessibility, performance, theming, responsive behavior, and whether the UI reflects real product state. Human findings and detector results were checked independently.

- **Browser verified** means I rendered the page or state in headless Microsoft Edge and inspected it. The desktop viewport was 1440 × 900. Narrow checks used 768 × 900 and 390 × 844. The live lab used seeded records and named role sessions. Seeded assessments can show a historical provider even while the header shows the active worker's Ollama adapter.
- **Code verified** means I traced the behavior to implementation. It is marked separately where a live outcome was unnecessary or would require writing data or running inference.
- **Audit limits** include physical touch devices, assistive-technology announcements, a full keyboard sweep, screen-reader testing, live Wazuh delivery, and measured frontend performance under production load. Decision and account forms were inspected before submission. The populated benchmark was rendered in the offline demo. No new real-provider benchmark was run.

### Impeccable technical assessment

| Dimension | Score | Basis |
| --- | ---: | --- |
| Accessibility | 1/4 | Alert dialog focus escapes, search is unnamed, and measured contrast is below AA in some controls and supporting labels. |
| Performance | 2/4 | The current Vite build reported about 536 kB of JavaScript before compression. All major views and demo data are reached through static imports. Runtime profiling and production performance were outside this audit. |
| Theming | 2/4 | Coherent dark base and existing tokens. Repeated raw palette utilities and loosely standardized sizes make contrast and states drift. |
| Responsive design | 1/4 | Sign-in reflows. The shared workspace rail squeezes operational screens, and the alert dialog uses nested scrolling at 390 px. |
| Implementation integrity | 2/4 | Domain-specific evidence and guardrails are strong. A status assertion and an inconsistent simulated score make the UI less trustworthy. |
| **Total** | **8/20** | Impeccable's rubric puts this in the range that needs substantial work. Use this score to prioritize design fixes. |

The biggest cognitive-load cost is the alert-review workspace. Four summary metrics, overlapping queue scopes, guardrail badges, runtime labels, and action buttons compete for attention. Keep findings, evidence, and human actions visible in that order. Give supporting metadata its own layer so it remains accessible on demand.

## Page-by-page recommendations

Priority reflects workflow impact. Effort is relative to the current codebase. Small changes stay in one or two surfaces, Medium changes coordinate several components or states, and Large changes affect layout or flow across roles.

### Sign-in, access, and global navigation

**1. Put recovery language first. High · Small · Stage 1.** The rendered sign-in fits at 390 px and preserves the username after a failed attempt, but the banner leads with “HTTP 401 Unauthorized,” the password placeholder is low contrast, and the protected route leads with “HTTP 403 FORBIDDEN.” Lead with “Check your username or password and try again” for invalid credentials, “Sign in again to continue” for an expired session, and “This page requires an Admin account” for the verified role restriction. Keep the return-to-queue action. Retain the associated labels and autocomplete attributes, announce errors through a live alert, and focus the relevant input. This preserves useful context and gives operators a recovery action at a glance. [Login](frontend/src/views/LoginView.tsx#L18) · [Protected route](frontend/src/components/layout/ProtectedRoute.tsx#L32) · [Invalid sign-in](.agents/codex/ui-ux-audit/03-login-invalid.png) · [Access denied](.agents/codex/ui-ux-audit/15-analyst-denied.png)

**2. Give narrow screens the full workspace width. High · Medium · Stage 2.** At 390 px, the measured sidebar claimed 255 px and left a 124 px main viewport, causing overflow and wrapping in the queue, analytics, and admin. Keep the desktop navigation rail. Below the width at which the workspace can fit, replace it with a compact header and a keyboard-accessible navigation drawer using the existing Base UI dialog primitive. Keep the active location and role visible, preserve one navigation item per permitted destination, and add a skip link to main content. Use `min-w-0` on the main flex child and keep horizontal scrolling inside genuinely two-dimensional data regions. This removes the broadest responsive blocker before rewriting any individual page. [Shell](frontend/src/components/layout/AppShell.tsx#L199) · [Existing dialog primitive](frontend/src/components/ui/dialog.tsx) · [390 px queue](.agents/codex/ui-ux-audit/06-queue-390.png) · [390 px analytics](.agents/codex/ui-ux-audit/17-analytics-390.png) · [390 px admin](.agents/codex/ui-ux-audit/24-admin-390.png)

### Analyst queue and alert review

**3. Show verified queue freshness. High · Small · Stage 1.** Edge showed a green “Stream Active” pill in replay mode. The label is unconditional. The queue updates on fetches triggered by the view. The summary presents abstention as a confidence-only rule, while the rule engine can abstain on other grounds. Show the matching count, a successful refresh timestamp from the most recent queue fetch, and the existing loading or unsuccessful refresh states. Offer a clearly labeled **Refresh queue** action using the existing handler. Use “Model deferred to analyst” and surface individual reasons in alert detail. Operators can use the timestamp to judge whether the queue reflects their latest fetch. [Queue fetch and labels](frontend/src/views/TriageQueueView.tsx#L101) · [Guardrail rules](backend/app/services/rules_engine.py) · [Rendered queue](.agents/codex/ui-ux-audit/04-queue-desktop.png)

**4. Keep the decision entry point visible. High · Medium · Stage 2.** At 1440 px, the populated table measured 1,672 px inside a 1,174 px main viewport. The inspection control was outside the initial horizontal view, although clicking a row opens the alert. Make severity, alert title, host, review state, and an explicit **Open alert** button the primary desktop columns. Keep the action at the visible edge or beside the alert title, and group confidence, guardrails, and ingestion time into secondary metadata. Use links or buttons with keyboard focus and clear names. On narrow layouts use compact alert rows with the same order and hide secondary fields behind the detail view. Consolidate the duplicate “Awaiting Review” labels into a primary **Review** tab and a distinct **Model assessment ready** subfilter. Move the no-results block outside the wide table and give search a real label. Operators gain a visible path from scanning to review at every width. **5. Make alert detail a real keyboard dialog. High · Small · Stage 1.** In a focused-control browser check, opening alert detail left focus on the queue's inspection button. The first Tab moved to the background **Quick approve** control. Escape dismissed the dialog and left focus on Quick approve. The component declares modal semantics and handles Escape manually. Wrap the existing panes in the local Base UI dialog primitives or equivalent scoped focus handling, focus the title or first meaningful control, and return focus to the invoking action on dismissal. Keep Escape and prevent background interaction while detail is open. A keyboard operator can stay in the review task and resume the queue at the same row. **6. Make evidence, decision, and audit three clear steps. High · Large · Stage 3.** The desktop dual-pane works for citation jumps, but the evaluated alert displayed repeated confidence, truncated path pills, diagnostic tabs, and several similarly prominent decisions. The 390 px dialog showed nested scrollbars and an action footer competing for height. Keep side-by-side evidence at wide widths. At narrow widths use one scroll container, a lightweight Assessment/Evidence switch, and one primary action. A citation should switch to Evidence, highlight the field and move focus to its target. Show a readable field name, such as **Command line**, with the exact path still available. Group raw JSON and the clearly labeled prompt reconstruction as diagnostics. Make **Decision history** a jump target and surface it first on closed alerts. Preserve existing server actions, confirmation rules, feedback behavior, stale-decision checks and manual-close semantics. This keeps the evidence path short while preserving the analyst's ability to inspect and audit the decision. **9. Make account and host forms accessible and specific. High · Small · Stage 1.** The rendered creation forms have visible labels, but code inspection shows several labels are unbound, including username/email and agent ID/hostname. Associate every control with `htmlFor` and `id`, use `aria-describedby` for limits and errors, focus the first invalid field, and keep one form-level cancel affordance. ## Proposed design direction

Keep Sentra-X's shield, wordmark, neutral dark surfaces, and restrained cyan evidence cues. Design for an analyst scanning alerts during a shift, a lead interpreting small cohorts, and an admin checking runtime configuration. Reserve the strongest visual emphasis for the active task.

| Element | Recommendation |
| --- | --- |
| Color | Use canvas `#09090B`, panels `#111113`, raised controls `#18181B`, primary text `#F4F4F5`, secondary text `#A1A1AA`, and subtle structural borders `#27272A` as starting tokens. Use a stronger accessible border or outline where a control's boundary identifies it. Keep white as the primary action and cyan for cited evidence and focus. Use red for critical severity or destructive action, amber for review or degradation, green for confirmed success, and neutral text for unavailable values. Pair status colors with text. Validate exact foreground/background pairs before adopting them. |
| Type | Keep Geist Variable. Use 24/32 px for page titles, 18/26 for section headings, 14/20 for prose and controls, and 12/16 for secondary labels. Use monospace and tabular numerals for timestamps, alert IDs, paths, code, and comparable measurements. Use normal case for navigation and form labels. |
| Spacing and surfaces | Use a 4 px base with 8, 12, 16, 24, and 32 px steps. Aim for 16 px panel padding on narrow screens and 24 px on desktop. Use a single border for ordinary panels, 8 px corners for controls, and 12 px for panels. Give dialogs elevation for layering. Remove decorative glow and pulsing status when they carry no state. |
| Navigation and pages | Use one compact role-filtered rail on wide screens and a drawer on narrow screens. Align page title, description, and one primary action consistently. Keep the operator's current section and filters when returning from detail. Reserve the account and runtime page for operations, with benchmark controls in the benchmark tab. |
| Tables and forms | Make a row's main task visible without horizontal travel. Use consistent headings, sticky headers where useful, right-aligned numbers, sensible truncation with a keyboard-accessible full value, and a scoped scroll container for wide data. Use labelled controls, visible focus, inline validation, and an explicit review step for consequential actions. |
| Dashboards and charts | Start with the report window and cohort, then show actionable totals and rates with denominators. Distinguish zero, insufficient sample, and unavailable results. Use chart markers, line patterns, and labels in addition to color. Keep an accessible numerical table or summary and an export that refers to the displayed filters. |
| States and feedback | Distinguish loading, empty, stale, partial, unavailable, and successful states. Preserve visible data during safe refreshes with a freshness message. Use restrained transitions for controls, support reduced motion, and keep buttons and forms in place during loading. Give success feedback next to the action and retain the audit reference where the workflow supplies one. |
| Accessibility and responsiveness | Target WCAG 2.2 AA. Check 4.5:1 for normal text and 3:1 for large text, plus relevant control and focus contrasts. Verify keyboard operation, accessible names, visible focus, focus restoration, and announcements. Use at least 24 × 24 CSS px pointer targets or a documented exception, and aim for 44 × 44 on compact touch controls. Check reflow at 320 and 390 px, tablet at 768 px, desktop at 1280 and 1440 px, and zoom. Keep horizontally scrollable exceptions scoped to data that needs two-dimensional layout. |
